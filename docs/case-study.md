# 产品案例｜为什么「已送达」不等于「已完成」？

**项目背景：** 秋招笔试附加题要求在 25 分钟内提交可访问的校园跑腿平台雏形，之后可以在原域名继续迭代。目标是展示产品结构和 AI 辅助开发能力，而非运营一套真实交易系统。

## 从一个真实感场景开始

一位同学从北门驿站回宿舍，愿意帮别人取一个小件。他首先要知道的是「顺不顺路、来不来得及」，不是发布者写了多长的描述。另一位同学关心的则是「谁接走了，有没有送到，怎么确认」。因此大厅优先展示路线、时限、感谢金；详情页承担交接说明和履约记录。

## 三轮迭代

1. **先交付一个可以点的链接。** 首版用少量示例实现发布、分类、接单与模拟完成，先部署再扩展。固定域名让评审不必更新书签。
2. **把一次点击“完成”拆成两个角色的动作。** 新版将发布、接单、送达、发布者确认和评价串起来。确认前不给履约分；发布者不能接自己的任务；评价不能重复加分。这些规则既体现在界面里，也写进自动测试。
3. **根据设备与回访场景改版。** 将侧栏改为桌面顶部导航和手机底部导航，用校园地图解释「顺路」；手机单列卡片便于阅读路线。回访时，过期样例可单独刷新，不必清空所有任务来重新体验。

## AI 在哪里帮上忙？

用 AI 生成页面与状态转换代码，再用可观察的验收条件约束它，而不是把“页面看起来完成了”当作交付。以下是可复用的验收提示词示例，非原始对话逐字记录：

```text
把送达和完成拆成两个动作。接单人送达后，状态应为“待确认”，信用不变；
只有发布者确认才加 3 分。同一任务重复确认或重复评价不得重复加分。
先写测试，再改模型；最后在浏览器从接单一路点到信用明细。
```

验证分为三层：[业务测试](../test-model.mjs)检查角色、状态和计分；[页面结构检查](../test-design.mjs)检查关键导航与移动端样式入口；浏览器交互检查验证搜索、接单、确认与数据刷新后的可用性。没有把示例次数当作真实用户或运营指标。

## 下一步如何做成多人产品

第一步不是加支付，而是让「两个人同时接一单」有明确结果：服务端原子接单、校内身份绑定、按角色控制状态变更，并把每次确认写入独立记录。只有这条链路可靠，才值得接入费用托管与纠纷处理。当前版本未实现这些服务。
